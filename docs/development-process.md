## 1. 总体技术路线

三层管线，数据单向流动：

```
┌─────────────┐   ┌──────────────────────┐   ┌─────────────────────────┐
│  数据层      │   │  建模层（离线）        │   │  呈现层（网页运行时）      │
│ OpenStreetMap│ → │ Blender              │ → │ React + Three.js        │
│ building /   │   │ 清洗 / 风格化 /       │   │ GLB 加载 / LOD /        │
│ waterway /   │   │ 景点精模 / GLB 导出   │   │ 拾取 / 标签 / 聚焦        │
│ attraction   │   │                      │   │                         │
└─────────────┘   └──────────────────────┘   └─────────────────────────┘
```

| 层 | 选型 | 说明 |
| :--- | :--- | :--- |
| 地图数据 | OpenStreetMap | building footprints、waterway、tourism/historic 景点节点、护城河边界 |
| 建模 | Blender | 导入 OSM → 清洗 → 风格化屋顶群 → 景点精模 → 导出 GLB |
| 网页端 | React + Three.js | 是否引入 @react-three/fiber 由团队习惯决定，不为 R3F 而 R3F |
| 模型格式 | GLB（glTF 2.0 binary）+ Draco | Three.js 原生支持最好，建筑群可压到原体积 20–30% |

## 2. 工具与依赖

| 用途 | 工具 | 备注 |
| :--- | :--- | :--- |
| OSM → Blender（免费路径） | BlenderGIS | 通过 Overpass API 按视口拉取，支持 `height` / `building:levels` 拉伸 |
| OSM → Blender（高质量路径） | Blender-OSM（blosm） | base 免费；premium 提供复杂屋顶、贴图与材质预设（是否采购见需求文档 Q2） |
| 拾取加速 | three-mesh-bvh | 用于景点射线拾取 |
| 标签 | CSS2DRenderer | 屏幕空间 HTML 标签 |
| 纹理压缩 | KTX2 + Basis Universal | 景点关键纹理 |
| 聚焦动画 | gsap 或手写 lerp | 二选一 |

**Overpass API 使用纪律**：Overpass 是共享免费服务，**禁止一次性拉取整个古城**。按 1 km × 1 km 或按街坊分块拉取，否则容易 406 超时。

## 3. 五阶段开发流程

五个阶段串行推进，每个阶段有明确的产出与验证标准。阶段内的任务可并行。

### 阶段 1：确定主城（坐标 + 轮廓）与艺术化处理

**目标**：锁定空间基准，确立"分层呈现"的艺术基调——先定基调，再谈细节。

步骤：

1. **锁定坐标基准**。古城边界取 120.5979°E–120.6447°E，31.2868°N–31.3345°N；场景原点取几何中心（约 120.621°E, 31.311°N），局部墨卡托或等比缩放，1 单位 = 1 米。
2. **提取古城轮廓**。从护城河 OSM 数据提取轮廓多边形，作为沙盘底座边界。
3. **确立三层呈现策略**（这是艺术化处理的第一决策，不是加细节）：
   - 底层肌理：OSM building footprints 做密度栅格化 → 风格化低模屋顶群（统一坡屋顶语言），不逐栋拉伸；
   - 水系骨架：完整保留"三纵三横一环"，作为视觉锚点；
   - 重点片区：平江路、山塘街、拙政园—狮子林片区单独划为精细区。
4. **确定分块单元**。以苏州古城保护规划的 54 个街坊作为内部分块加载与 LOD 的逻辑单元（分块只服务于加载，呈现上仍是一整块沙盘）。

- **产出**：坐标与单位约定、古城轮廓多边形、三层呈现策略、街坊分块划分。
- **验证**：打开页面能看到正确的城形和"三纵三横一环"。

### 阶段 2：搭建立体场景（OSM → Blender → Three.js）

**目标**：把 OSM 数据变成可渲染的立体基底。

步骤：

1. **导入 OSM**。按 1 km × 1 km 或街坊分块拉取（BlenderGIS 或 blosm），开启 extrude 并读取 `height` / `building:levels`。
2. **清洗数据**（必做）：
   - Merge by Distance 焊接重复顶点；
   - 删除高度异常值（如误标 `height=200`），压回合理范围；
   - 无高度标签的民居交给工具 fallback 高度——这是信号而非缺陷，后续归入风格化屋顶群。
3. **生成风格化屋顶群**。在 Blender 中用几何节点或散布方式，按密度场生成统一坡屋顶语言的低模屋顶群。
4. **制作场景基底**。轮廓多边形做"抬升的沙盘底座"（底面加厚度），底座外侧放简化环城河水面。
5. **布光**。HDRI 环境光 + 一盏方向光：方向光负责阴影轮廓，HDRI 提供环境反射，避免多光源在低模场景产生噪点阴影。
6. **导出**。统一 GLB，建筑群开 Draco 压缩。
7. **网页端接入**。初始化 Three.js 场景与相机，加载首屏内容（底座 + 水系 + 全域 L0 占位）。

- **产出**：底座、水系、全域风格化建筑群（GLB），可运行的首屏场景。
- **验证**：L0 全景稳定 30 FPS，draw call < 30。

### 阶段 3：制作景点模型

**目标**：为高辨识度景点制作精细模型，嵌入底模。

步骤：

1. **按优先级排产**。P0：拙政园、留园、平江历史街区（样板段）、盘门；P1：网师园、狮子林、山塘街、苏州博物馆；P2：沧浪亭、寒山寺。清单与说明见需求文档 FR-05。
2. **定位**。从 OSM `tourism=attraction` / `historic=*` 节点读取坐标作为定位基准；拙政园、留园、网师园等世界遗产用公开经纬度校验。
3. **建模**。每个景点控制在 5k–30k 三角面（不含植被）；用 Decimate（collapse 模式）在保持轮廓前提下压面，**不要用 unsubdivide**（会破坏园林曲线屋顶和假山的剪影）。
4. **材质**。走 Principled BSDF → glTF 导出兼容路径，避免复杂节点树；需要砖瓦纹理时烘焙成一张 1024×1024 base color + 一张 normal map，随 GLB 嵌入或单独存放。
5. **嵌入底模**。在 OSM 底模对应位置把建筑体块置空或压平，再放置精细模型，避免 z-fighting。景点模型单独成 GLB，加载后放入 `THREE.Group`，不参与实例化。

- **产出**：各景点独立 GLB，已嵌入底模。
- **验证**：景点模型在 L2 下可读，面数在预算内。

### 阶段 4：优化模型（面向 Web 的硬性预算）

**目标**：在主流笔记本集显上稳定 30 FPS 以上。预算见需求文档第 5 节。

步骤：

1. **几何合批**。全域建筑群按材质/类型合并为少量 BufferGeometry，屋顶语言统一时直接用 InstancedMesh（实测参考：2700 栋独立建筑约 2 FPS，切 InstancedMesh 后拉开视距可回到 200 FPS 级别；苏州古城全域万栋以上，无实例化几乎不可行）。景点用 `three-mesh-bvh` 加速拾取。
2. **纹理控制**。总纹理内存 ≤ 100 MB；建筑底模用顶点颜色或纯色材质；景点关键纹理用 KTX2 + Basis Universal（`KTX2Loader` 加载）；HDRI 用 2K。
3. **实现三级 LOD**：

| 层级 | 视距 | 内容 |
| :--- | :--- | :--- |
| L0 | >800 m | 底座 + 水系 + 极简实例 + 景点占位体块，draw call ≤ 20 |
| L1 | 200–800 m | 带屋顶语言实例（坡顶/平顶两类）+ 景点中模（2k–5k 面） |
| L2 | <200 m | 景点高模 + 视锥内近处 200–300 栋实例，远处留在 L1 |

4. **分块加载**。按街坊或 1 km 网格打包建筑群 GLB，用 `LoadingManager` 监控进度；首屏只加载底座 + 水系 + 全域 L0 占位，景点与精细建筑块异步按需加载。

- **产出**：实例化建筑群、三级 LOD、分块异步加载。
- **验证**：集显 30 FPS，拉近/推远无卡顿。

### 阶段 5：加入交互

**目标**：完成核心交互四件事。技术栈 React + Three.js（R3F 与否取决于团队习惯；若用 R3F，Canvas 管理相机与事件，业务状态用 React state 驱动高亮与标签显隐）。

步骤：

1. **轨道控制**。`OrbitControls` 开 damping，限制 `polarAngle` 防止镜头穿地，`minDistance` / `maxDistance` 对应 L2 / L0 切换阈值附近。
2. **射线拾取 + 高亮**。`Raycaster` + `three-mesh-bvh` 检测景点与建筑点击；高亮优先改 `material.emissive`，共享材质先 clone 再改，避免"串亮"；点击建筑实例时通过 `instanceId` 解析 OSM id 或自定义数据，触发 HUD 面板。
3. **标签系统**。`CSS2DRenderer` 将 HTML 钉在 3D 坐标；显隐层级 L0 只显示 P0 景点、L1 显示全部、L2 显示子标注（如"远香堂""冠云峰"）；处理遮挡——被前方建筑挡住时降低透明度。
4. **景点聚焦**。点击标签或模型后相机平滑 focus 到景点包围盒（gsap 或手写 lerp）；返回全景用同一套动画反向执行；侧边栏/HUD 展示景点名称、简介、是否世界遗产等静态信息。

- **产出**：轨道控制、拾取高亮、标签、聚焦与信息面板。
- **验证**：点击景点有 HUD 响应，标签层级正确，聚焦/返回平滑。

## 4. 里程碑与验收

| 阶段 | 产出 | 关键验证 |
| :--- | :--- | :--- |
| M0（1 周） | 古城轮廓底座 + 水系 + 坐标系锁定 | 打开页面能看到正确的城形和"三纵三横一环" |
| M1（2 周） | OSM 建筑群分块导入 → 风格化屋顶群 → InstancedMesh 上屏 | L0 全景稳定 30 FPS，draw call < 30 |
| M2（2–3 周） | 3 个 P0 景点精细模型（拙政园、盘门、平江样板段） | 景点模型在 L2 下可读，面数在预算内 |
| M3（1–2 周） | LOD 切换、分块加载、Raycaster 拾取 + CSS2D 标签 | 拉近/推远无卡顿，点击景点有 HUD 响应 |
| M4（持续） | 剩余景点补齐、纹理/光照打磨、移动端降级 | 集显 30 FPS、独显 60 FPS |

> 注：留园同为 P0 景点，若 M2 产能允许则一并完成，否则在 M4 补齐（见需求文档 FR-05 与 S-03）。

## 5. 风险与备选方案

| 风险 | 应对 |
| :--- | :--- |
| **最大风险：全貌与细节的预算冲突**。全域逐栋建筑在 Web 端不可行 | 核心策略："风格化屋顶群 InstancedMesh + 景点嵌入"分层。若 M1 实例化后 draw call 仍偏高，备选：在 Blender 中按材质合并为 1–3 个整体 mesh，放弃逐栋交互，仅保留景点与关键街区可拾取——沙盘"全貌"体验不依赖点击每栋民居 |
| Overpass 拉取超时（406） | 严格按 1 km × 1 km 或街坊分块拉取，不整城拉取 |
| 集显性能不达标 | 优先压 draw call 与纹理内存，降 HDRI 至 1K、收紧 L2 实例数量 |
| 景点面数超预算 | Decimate（collapse）压面，禁用 unsubdivide |

## 6. 关键决策记录

| 决策 | 结论 | 依据 |
| :--- | :--- | :--- |
| 呈现单位 | 1 单位 = 1 米，原点在古城几何中心 | LOD 距离参数按真实尺度设定 |
| 建筑呈现 | 风格化屋顶群，不逐栋拉伸 | 14 km² 数万栋 extrude 会触发 draw call 灾难 |
| 模型格式 | GLB + Draco | Three.js 原生支持最好，压缩比高 |
| 景点与底模关系 | 嵌入而非覆盖 | 避免 z-fighting |
| 是否用 R3F | 团队习惯决定，不为 R3F 而 R3F | 声明式与命令式均可行 |
