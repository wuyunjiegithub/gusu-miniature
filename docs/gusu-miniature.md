### 步骤 1：确定主城范围与艺术化处理

**坐标基准**。苏州古城的经纬度边界可取 **120.5979°E–120.6447°E，31.2868°N–31.3345°N**，这是中研院 GIS 苏州城图中标注的 bounds，与当代护城河以内范围基本吻合。古城本体面积 **14.2 km²**，南北约 4600 m，东西约 3400 m，形状为“略带屈曲的长方形”。在 Three.js 中建议以古城几何中心（约 120.621°E, 31.311°N）为原点做局部墨卡托或简单等比缩放，单位用米，1 单位 = 1 米，方便后续 LOD 距离参数直接按真实尺度设定。

**艺术化处理的第一个决策不是“加细节”，而是“定基调”**。完整 OSM 建筑体块在 14 km² 尺度下会产生数万栋 Extrusion，直接导入 Three.js 必然触发 draw call 灾难。建议将场景分为三层：

- **底层肌理（OSM 派生）** ：不追求每栋建筑精确，而是提取**建筑密度场**和**街巷/水系网络**。用 OSM 的 building footprints 做密度栅格化，生成“哪里是密集民居、哪里是园林绿地、哪里是主干道”的底图，然后在 Blender 中用几何节点或散布方式生成风格化的低模屋顶群（统一坡屋顶/双坡顶语言），而不是逐栋拉伸。
- **水系骨架**：苏州古城“三纵三横一环”的水系是沙盘辨识度的第一来源。OSM 的 waterway 数据相对可靠，应完整保留，并在 Three.js 中用略深的材质和轻微反光突出，作为视觉锚点。
- **重点片区**：平江路、山塘街、拙政园—狮子林片区等，单独划定“精细区”，这些区域才使用真实 OSM 建筑轮廓做较高精度的体块。

这种分层让“全貌”可读，又不必在全域为每栋民居建模。苏州古城保护规划中常用的**街坊单元**（54 个街坊）可以作为内部分块加载的逻辑单元，但与呈现无关——呈现层面仍是一整块沙盘，分块只服务于加载和 LOD。

### 步骤 2：搭建立体场景（OSM → Blender → Three.js）

**OSM 导入工具选择**。两条路径都可行：

- **BlenderGIS**：免费，通过 Overpass API 按视口范围拉取，开启 extrude 后读取 `height` 和 `building:levels` 标签拉伸。适合快速拿到试验区。注意 Overpass 是共享免费服务，**一次不要拉整个古城**，按 1 km × 1 km 或街坊分块拉取，否则容易 406 超时。
- **Blender-OSM（blosm）** ：导入质量更高，支持复杂屋顶形状、地形和道路宽度，base 版本免费、premium 版本提供贴图和材质预设。如果预算允许，premium 版在“沙盘艺术化”阶段能省去大量材质调整时间。

导入后**必须做清洗**：Merge by Distance 焊接重复顶点，删除高度异常值（OSM 中偶见 `height=200` 之类的误标），将明显不合理的建筑压回合理范围。苏州古城内大量民居无高度标签，BlenderGIS 会给 fallback 高度——这正好，因为我们的策略本就不是保留每栋的真实高度，而是把“无标签”作为信号，归入风格化屋顶群处理。

**场景基底**。地面用古城轮廓多边形（可从护城河 OSM 数据提取）做“抬升的沙盘底座”，底面加一圈厚度，形成实体沙盘台的观感。底座外侧可以放简化的环城河水面。光照建议使用 **HDRI 环境光 + 一盏方向光**，方向光负责阴影轮廓，HDRI 提供环境反射，避免多光源在低模场景中产生噪点般的阴影。

**导出格式**：统一 **GLB（glTF 2.0 binary）** 。Three.js 原生支持最好，Draco 压缩可把建筑群几何压到原体积的 20–30%。

### 步骤 3：制作景点模型

苏州古城内值得作为独立高精度模型呈现的景点，建议控制在 **8–12 个**。以下清单按“沙盘辨识度”和“O SM 底座是否够用”筛选：

| 景点                    | 类型     | 建模优先级 | 说明                                               |
| :---------------------- | :------- | :--------- | :------------------------------------------------- |
| 拙政园                  | 园林     | P0         | 沙盘东部的视觉重心，水系和亭廊轮廓需要手工         |
| 留园                    | 园林     | P0         | 西部锚点，冠云峰和曲廊的体量关系是识别关键         |
| 网师园                  | 园林     | P1         | 中小型园林代表，适合展示“精致度”                   |
| 狮子林                  | 园林     | P1         | 假山群的几何复杂度高，需控制面数                   |
| 平江历史街区            | 街区     | P0         | 不需要每栋建模，但沿河立面需要一段“样板段”精细处理 |
| 盘门（瑞光塔+水陆城门） | 地标     | P0         | 古城西南角唯一的“垂直地标”，塔是沙盘天际线的关键   |
| 山塘街（阊门—虎丘段）   | 街区     | P1         | 西北方向线性地标，可做带状简化模型                 |
| 苏州博物馆              | 现代地标 | P1         | 与拙政园相邻，体量简洁，低模即可传达特征           |
| 沧浪亭                  | 园林     | P2         | 南部锚点，复廊和水面关系有辨识度                   |
| 寒山寺                  | 宗教     | P2         | 位于阊门外，是否纳入取决于主城范围是否扩展到枫桥   |

景点坐标可以从 OSM 的 `tourism=attraction` 或 `historic=*` 节点直接读取并作为定位基准；拙政园、留园、网师园等世界遗产的精确经纬度也有公开记录可校验。

**建模原则**：每个景点模型控制在 **5k–30k 三角面**（不含植被），用 **Decimate（collapse 模式）** 在保持轮廓的前提下压面，不要用 unsubdivide（对园林的曲线屋顶和假山会破坏剪影）。材质走 **Principled BSDF → glTF 导出兼容** 的路径，避免复杂节点树；如果需要砖瓦纹理，在 Blender 中烘焙成一张 1024×1024 的 base color + 一张 normal map，随 GLB 嵌入或单独存放。

景点模型与 OSM 底模的关系是 **“嵌入”而非“覆盖”**：在 OSM 底模的对应位置把建筑体块置空或压平，然后将精细模型放置在该位置，避免 z-fighting。

### 步骤 4：优化模型（面向 Web 的硬性预算）

这一步的目标不是“尽量好看”，而是**在主流笔记本集显上稳定 30 FPS 以上**。

**几何层面**：

- 全域 OSM 派生建筑群：**按材质/类型合并为少量 BufferGeometry**，或者如果屋顶语言统一，直接用 **InstancedMesh** 绘制。有实测案例显示，2700 栋独立建筑在 draw call 层面会把帧率拉到 2 FPS，切换到 InstancedMesh 后拉开视距可回到 200 FPS 级别。苏州古城全域建筑量级在万栋以上，没有实例化合批几乎不可行。
- 精细景点模型：每个景点单独一个 GLB，加载后放入 `THREE.Group`，不参与实例化。用 **`three-mesh-bvh`** 加速后续的射线拾取，景点数量少，BVH 构建开销可以接受。

**纹理层面**：总纹理内存控制在 **100 MB 以内**（WebGL 上下文的安全区）。建筑底模尽量用**顶点颜色或纯色材质**而非贴图；景点模型的关键纹理用 **KTX2 + Basis Universal** 压缩，Three.js 的 `KTX2Loader` 可直接加载。HDRI 用 2K 分辨率（1K 在沙盘尺度下高光会糊，4K 对集显压力过大）。

**LOD 策略**：沙盘是俯瞰视角为主、局部拉近查看景点，适合**基于距离的 3 级 LOD**：

- **L0（>800 m）** ：全域只渲染底座 + 水系 + 建筑群 InstancedMesh 的极简版本（每栋一个 box 或单坡屋顶）+ 景点用一个“占位体块”，总 draw call 控制在 20 以内。
- **L1（200–800 m）** ：建筑群切换到带屋顶语言的 InstancedMesh（两种实例类型：坡顶、平顶），景点开始显示中模（约 2k–5k 面）。
- **L2（<200 m）** ：景点切换到高模，建筑群视锥内仅保留近处 200–300 栋的实例，远处实例 scale 置零或留在 L1 层级。

**加载策略**：按街坊或 1 km 网格分块打包建筑群 GLB，用 `LoadingManager` 监控进度，首屏只加载底座 + 水系 + 全域 L0 占位，景点模型和精细建筑块异步按需加载。这对于“打开就要看到古城全貌”的沙盘体验至关重要。

### 步骤 5：加入交互

技术栈：**React + Three.js**。具体是否用 `@react-three/fiber` 取决于团队习惯。R3F 在声明式管理场景层级、HUD 组件和事件生命周期上有明显优势，但如果团队更熟悉纯 Three.js 的命令式流程，直接用 `THREE.Scene` + React 外壳也完全可行，**不要为了 R3F 而 R3F**。如果选择 R3F，Canvas 管理相机和事件，业务状态通过 React state 驱动高亮和标签显隐，是成熟的模式。

**核心交互四件事**：

**① 轨道控制**：`OrbitControls` 开启 damping，限制 `polarAngle` 避免镜头穿到地面以下，`minDistance` 和 `maxDistance` 对应 L0 和 L2 的切换阈值附近。

**② 射线拾取 + 高亮**：用 `Raycaster` 配合 `three-mesh-bvh` 做景点和建筑的点击检测。高亮优先改 `material.emissive`，对共享材质要 clone 后再改，避免“串亮”。点击建筑群中的实例时，通过 `instanceId` 解析出对应的 OSM id 或自定义数据，触发 HUD 面板。

**③ 标签系统**：景点标签用 **`CSS2DRenderer`**，将 HTML 元素钉在 3D 坐标上。CSS2D 的好处是文字锐利、样式用 CSS 控制、不需要在纹理里烘焙文字，适合沙盘上“拙政园”“盘门”这类需要清晰可读的标注。控制标签的显隐层级：L0 只显示 P0 景点，L1 显示全部景点，L2 可显示景点内的子标注（如“远香堂”“冠云峰”）。标签要处理遮挡——当标签所在位置被前方建筑挡住时降低透明度，否则俯瞰时标签会“浮”在无关区域上。

**④ 景点聚焦**：点击标签或模型后，相机平滑 `focus` 到该景点的包围盒，用 `gsap` 或手写 lerp 均可。返回全景用同一套动画反向执行。侧边栏 / HUD 展示景点名称、简介、是否世界遗产等静态信息即可，沙盘不需要做复杂的 UI 状态管理。



| 阶段         | 产出                                                   | 关键验证                                 |
| :----------- | :----------------------------------------------------- | :--------------------------------------- |
| M0（1 周）   | 古城轮廓底座 + 水系 + 坐标系锁定                       | 打开页面能看到正确的城形和“三纵三横一环” |
| M1（2 周）   | OSM 建筑群分块导入 → 风格化屋顶群 → InstancedMesh 上屏 | L0 全景稳定 30 FPS，draw call < 30       |
| M2（2–3 周） | 3 个 P0 景点精细模型（拙政园、盘门、平江样板段）       | 景点模型在 L2 下可读，面数在预算内       |
| M3（1–2 周） | LOD 切换、分块加载、Raycaster 拾取 + CSS2D 标签        | 拉近/推远无卡顿，点击景点有 HUD 响应     |
| M4（持续）   | 剩余景点补齐、纹理/光照打磨、移动端降级                | 集显 30 FPS、独显 60 FPS                 |

**最大风险不在建模，在“全貌”与“细节”的预算冲突**。OSM 全域逐栋建筑在 Web 端不可行，方案的核心应对是 **“风格化屋顶群 InstancedMesh + 景点嵌入”** 的分层策略。如果 M1 阶段发现即使实例化后建筑群 draw call 仍偏高，备选方案是将全域建筑群在 Blender 中**按材质合并为 1–3 个整体 mesh**，放弃逐栋交互，只保留景点和关键街区的可拾取性——沙盘的“全貌”体验不依赖于点击每一栋民居。
