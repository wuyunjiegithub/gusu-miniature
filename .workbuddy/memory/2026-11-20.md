## 常识性几何检查（断头路 / 压路 / 通水 / 山形）

用户提的四条硬要求：不要断头路、房子别盖在马路上、路别通进水里、寒山寺旁的山别像富士山。

### 桥：真正的坑是桥宽只有路宽的一半
- `src/utils/bridges.ts` 里 `halfWidth` 原来写死 `major:6.4 / minor:4.2`，而 `Roads.tsx` 实际路宽是 `MAJOR_WIDTH=26 / MINOR_WIDTH=11`（半宽 13 / 5.5）。
- 后果：桥只有路的一半宽，路面自身的 ribbon 把桥盖住了 → 看上去就是"路直接压过水面"，桥上栏杆完全看不见。
- 改法：`halfWidth = major:13.4 / minor:5.8`（略宽于路面，栏杆露在路缘外）。改完护城河、山塘河、城内河上的桥才真正"看得出来"。
- 同时给长桥加缓拱：`edgeY = max(waterY+1.15, roadY+0.55)`，`camber = min(2.4, 0.75 + span*0.013)`，`crownY = edgeY + camber`；引坡长度改为按高差自适应 `max(9, (edgeY-roadY)*7)`，避免坡比超过 12% 变成台阶。
- 桥位现状（`node scripts/qa-bridges.mjs`）：护城河 9 座、城内河 2 座、山塘河 5 座。护城河跨度 81–135m，山塘河 23–32m。

### 山体：富士山感的两个来源
- `src/components/Hills.tsx`：`mask=0` 的区域原来整片照画，等于在山脚外铺了一块 1520×790m 的浅色平板，和带贴图的地面撞成"台座"。
  → 改法：逐格判断，`max(四角高度) < TOE_EPS(0.35m)` 的三角形直接不生成。
- 山顶色原来用 `hillHigh`（春夏季 `#7e9077` 浅灰绿），配上圆滑轮廓就是雪顶富士山。
  → 改法：非冬季山顶走岩石色 `#8a8478`，只有冬季才用 `hillHigh` 转白；`createHillGeometry` 新增 `winter` 参数。
- 山脚色带：`plain(land)` → `foot` 的过渡原来是 0～5% 高度（≈9m），拉出一圈很宽的灰白环。
  → 收到 0～1.5%；`foot` 改为 `lowHex.lerp(lawnHex, 0.22)` 偏林色；`plain` 乘 0.83（山脚几乎贴地、受满日照，原色会比带贴图的地面亮）。
- 形态：`mask = pow(1-smoothstep(0.3,1.0,q), 0.55)`（山腰陡、山脚缓的凹形坡）；两级 ridge 噪声 + `lean` 不对称项；`edgeWobble` 改三频叠加。

### 建筑压路的判定偏保守
- `scripts/qa-geometry.mjs` 报 2244 处"压路"，但实测最深那处（-655,-2011）建筑离路面有明显退距——它用的是定向包围盒四角判定，对异形/长条建筑偏严。视觉上城内已没有房子盖在车道中间。

### 已知但没动的
- 城内河道水面 Y=2.4，比路面（1.2–1.3）高 1.1m。属于 `CanalEmbankment` 驳岸体系（压顶同 2.4m）的一部分，改动会牵连驳岸/水门/桥，风险大于收益，暂留。
- 地铁线在水面处被 `clipToLand` 剪断，视觉上会"停在河边"，语义上算地下隧道，可接受。

## 第三轮：首屏卡死（用户报"载入项目会卡住，过一会再出来"）

### 定位方法（可复用）
- `scripts/perf-load.mjs`：导航各阶段耗时 + longtask 累计阻塞 + 最慢资源。
  注意 headless + SwiftShader 下每帧渲染本身就几百毫秒，longtask 数字会被软件光栅化撑大，
  只能看**首屏那几秒**的长任务，不能当成用户机器上的绝对值。
- `scripts/perf-profile.mjs`：CDP `Profiler.start/stop` 采 200µs 粒度样本，按**自身耗时**排序。
  这个是唯一靠谱的手段——一眼看出 `computeBridgeSites → waterLevelAt → distToSeg` 占了 5.3 秒。
- `scripts/perf-boot.mjs`：按 400/1200/2500/4000/7000/12000ms 截图并读 `#boot` 状态，验证启动页过渡。

### 根因：每一处"点到折线距离"都是全量遍历
性能采样（改造前 21s 窗口）：
```
5322ms  distToSeg@bridges.ts     <- computeBridgeSites -> waterLevelAt
1967ms  pointInRing@geo.ts       <- Trees / Transit
1212ms  nearestRoadInfo@outerCity.ts (+578ms roadNear, +153ms boxHitsRoad)
 886ms  pointInPolygon@bridges.ts
 781ms  pointInRing@Transit.tsx   (+652ms distToLine, +450ms NightLights)
```
道路按 4m 采样共 33 万个点，每个点对 270 段水道折线逐条 `Math.hypot` 求最小值 → 8000 万次开方。
`Math.hypot` 本身比手写 sqrt 慢近一个数量级，是最大的放大器。

### 改法
1. **新增 `src/utils/waterField.ts`**：全场景唯一的水面判定入口。
   把所有水道线段（河道 162 / 山塘 / 护城河 100）一次性装进 64m 均匀网格，查询只测当前格子里的候选段；
   距离用平方比较，不开方。导出 `waterLevelAt(x,z,margin)` / `inWater(x,z,margin)`。
   优先级保持 河道 > 山塘河 > 护城河；护城河必须取"到轮廓的**最短**距离"再判环带，
   否则盘门那种内凹处会误判（第一版就踩了这个坑，比对脚本报 86/583443 不一致）。
2. **`src/utils/geo.ts` 的 `pointInRing` 加 z 分桶索引**（96 桶，WeakMap 按 ring 缓存）。
   100 点环单次查询从 100 次比较降到 1~3 次，结果与遍历法逐点一致。
3. **`bridges.ts` / `NightLights.tsx` / `Transit.tsx` 删掉各自的 `distToLine` 副本**，统一走 waterField。
4. **`outerCity.ts`**：`nearestRoadInfo` 改成 `hitsRoad` 返回布尔、平方距离、零对象分配；
   网格键从 `` `${cx},${cz}` `` 换成整数编码 `(cx+512)*1024+(cz+512)`。
5. **`vite.config.ts`** 加 `server.warmup.clientFiles`：dev server 启动时预转换入口依赖图，
   第一次打开不再吃那条"每个模块 80ms"的瀑布。
6. **`gl.debug.checkShaderErrors = false`（仅生产）**：每个 program 链接后 three 都会同步读 shader 日志。

### 效果（同一台机器、同样 21s 采样窗口）
| 项 | 改造前 | 改造后 |
|---|---|---|
| computeBridgeSites 整条链 | 6.9s | 0.17s |
| pointInRing(geo) | 1.97s | 0.04s |
| 城外地块压路判定 | 1.2s+0.58s | 0.17s |
| Transit 剪水面 | 1.4s | 不在榜上 |
| 主线程 idle 占比 | 2.2% | 70% |

剩余大头是 `onFirstUse`（three 首次使用 program 时 getUniforms + 链接）约 1.5~2.4s，
在 SwiftShader 下被放大，真实 GPU 上远低于此；已用生产环境关 checkShaderErrors 削掉一部分。

### 启动页：让"卡住"变成"有反馈"

### 等价性校验（`scripts/qa-waterfield.mjs`）
